# Autenticación

Atlas autentica a dos tipos de personas, siempre dentro de un tenant:

- **Miembros** (lectores, oyentes, espectadores): inician sesión con un **enlace de acceso sin contraseña**.
- **Operadores del tenant**: inician sesión con correo y contraseña (y un código TOTP si lo tienen activado).

Ambos terminan con un **JWT** que envía como `Authorization: Bearer <token>`. Los servidores que aprovisionan miembros usan
otra credencial, la [clave de integración](/docs/saas/atlas-api/integration-keys).

> No es el modelo de dos tokens de la 1Platform API. Si ve un header `x-user-token` en la
> [Referencia de API](/api-reference/atlas-api#tag/auth), ignórelo: no forma parte de la autenticación de Atlas y no
> debe enviarlo.

Todas las operaciones de esta página van con `X-Tenant-Slug`. Antes de empezar,
[verifique su slug](/docs/saas/atlas-api/tenant-resolution#verifica-tu-slug-antes-de-integrar): un slug mal escrito enviaría
el enlace de acceso desde otro tenant.

## Paso 1 — Envíe el enlace de acceso {#paso-1--envía-el-enlace-de-acceso}

`POST /auth/magic-link` envía un correo al miembro (de registro si el correo es nuevo, de inicio de sesión si ya existe). El
enlace dura 15 minutos por defecto; cada tenant puede ajustarlo.

```bash
curl -s -X POST "$ATLAS_BASE/auth/magic-link" -H "X-Tenant-Slug: $TENANT_SLUG" \
  -H "Content-Type: application/json" \
  -d '{ "email": "lector@example.com", "return_url": "/catalogo", "surface": "web" }'
```

**Dónde aterriza el enlace.** En el dominio principal del tenant, en `/auth/verify?token=…`. Con `surface: "app"` aterriza
en una página puente que intenta abrir la app nativa del tenant. En los dos casos, quien opera ese frente es quien recibe el
`token` y debe canjearlo en el paso 2. `return_url` es opcional y sólo aplica a `surface: "web"`: si envía una ruta relativa
segura del sitio, el sitio vuelve ahí tras el canje; si no la envía, o no es una ruta relativa segura, se descarta sin error
y el sitio usa su página de destino predeterminada.

Si el envío del correo falla, recibe `503 EMAIL_DELIVERY_FAILED` con `Retry-After`. El token ya se generó, así que puede
pedir un enlace nuevo pasado ese intervalo.

## Paso 2 — Canjee el token por una sesión {#paso-2--canjea-el-token-por-una-sesión}

`POST /auth/magic-link/verify` canjea el token de un solo uso. El primer canje crea el miembro para ese tenant y correo; no
hay un paso de registro aparte.

```bash
curl -s -X POST "$ATLAS_BASE/auth/magic-link/verify" -H "X-Tenant-Slug: $TENANT_SLUG" \
  -H "Content-Type: application/json" -d '{ "token": "<TOKEN_DEL_ENLACE>" }'
```

La sesión trae un token de acceso (24 h por defecto, indicado en `expires_in`), un token de refresco (30 días) y los roles
del miembro (`fan`). Un token ya usado, vencido o inválido responde `401` con `TOKEN_CONSUMED`, `TOKEN_EXPIRED` o
`TOKEN_INVALID`; un miembro bloqueado por el operador recibe `401 CREDENTIALS_INVALID`. Si envía en `device_fingerprint`
un identificador de dispositivo nuevo para el miembro, Atlas le manda un aviso de seguridad por correo; ese aviso nunca
bloquea el inicio de sesión.

## Paso 3 — Llame con el token de acceso {#paso-3--llama-con-el-token-de-acceso}

```bash
curl -s "$ATLAS_BASE/me" -H "X-Tenant-Slug: $TENANT_SLUG" -H "Authorization: Bearer $ATLAS_JWT"
```

Los navegadores del sitio del tenant usan la cookie `atlas_session`; desde su servidor use siempre el header `Authorization`.
Un token de acceso vencido, mal formado o ausente responde `401 UNAUTHORIZED` (no `TOKEN_EXPIRED`): esa es la señal para
refrescar. En las operaciones del miembro, un token emitido para otro tenant que el resuelto responde `403 TENANT_MISMATCH`.
Las operaciones del miembro (perfil, progreso, listas, sesiones) están en
[Referencia de API → me](/api-reference/atlas-api#tag/me).

## Paso 4 — Refresque antes de que venza {#paso-4--refresca-antes-de-que-venza}

`POST /auth/refresh` cambia el token de refresco por una sesión nueva sin otro correo. Un token de refresco vencido responde
`401 TOKEN_EXPIRED`; uno emitido para otro tenant, o anterior a un bloqueo del miembro, responde `401 TOKEN_INVALID`. En
ambos casos, pida un enlace de acceso nuevo.

```bash
curl -s -X POST "$ATLAS_BASE/auth/refresh" -H "X-Tenant-Slug: $TENANT_SLUG" \
  -H "Content-Type: application/json" -d '{ "refresh_token": "<REFRESH_TOKEN>" }'
```

:::warning El refresco siempre emite roles de miembro
La sesión que devuelve el refresco lleva sólo el rol `fan` y ningún permiso sobre otros tenants, aunque la original fuera
de operador. Para una sesión de operador, no refresque: vuelva a iniciar sesión con `POST /auth/admin/sign-in` cuando venza
el token de acceso.
:::

## Inicio de sesión de operador {#inicio-de-sesion-de-operador}

Los operadores del tenant no usan enlaces de acceso. `POST /auth/admin/sign-in` recibe correo, contraseña y, si la cuenta
tiene TOTP, el código. La sesión trae los roles `admin`, `operator` y `fan`, que habilitan la
[gestión de contenido](/docs/saas/atlas-api/content-management) y las operaciones `/admin/*`.

```bash
curl -s -X POST "$ATLAS_BASE/auth/admin/sign-in" -H "X-Tenant-Slug: $TENANT_SLUG" \
  -H "Content-Type: application/json" \
  -d '{ "email": "operador@example.com", "password": "<CONTRASENA>", "totp_code": "123456" }'
```

Credenciales incorrectas responden `401 CREDENTIALS_INVALID`; falta el código TOTP: `401 TOTP_REQUIRED`; código
incorrecto: `401 TOTP_INVALID`. La cuenta de operador la crea el equipo de 1Platform Labs. Si el operador olvida su
contraseña, `POST /auth/admin/forgot-password` envía un enlace de restablecimiento (responde igual exista o no la cuenta) y
`POST /auth/admin/reset-password` fija la nueva; después vuelva a iniciar sesión, con TOTP si la cuenta lo tiene.

Una cuenta de operador trabaja sobre su propio tenant: en las operaciones `/admin/*` el tenant sale del token, no de
`X-Tenant-Slug`. Sólo si tiene permiso explícito sobre otros tenants puede elegir uno con el header `X-Admin-Tenant-Slug`.
Con una cuenta sin ese permiso, cualquier slug distinto del propio responde `403 TENANT_SWITCH_FORBIDDEN`: no lo envíe. Un
slug permitido que no existe o está desactivado responde `400 TENANT_SWITCH_INVALID`.

## Roles

Una operación que exige un rol que la sesión no tiene responde `403 INSUFFICIENT_ROLE`; una que exige un permiso concreto
de contenido responde `403 INSUFFICIENT_PERMISSION`. Los operadores pueden emitir tickets de entrega sin derecho de acceso,
porque son dueños del catálogo.

## Sesiones y cierre de sesión

`POST /auth/sign-out` no invalida nada en el servidor: el sitio borra su cookie y el token de acceso sigue vigente hasta que
vence. `GET /me/sessions` lista los dispositivos del miembro, y `DELETE /me/sessions/{session_id}` o `DELETE /me/sessions`
los quitan de esa lista. `DELETE /me/sessions` conserva sólo el dispositivo cuyo `device_fingerprint` envíe; sin ese
parámetro, los quita todos. Quitar un dispositivo **tampoco** invalida los tokens ya emitidos: siguen vigentes hasta que
vencen. Trate la duración del token de acceso como el límite real de una credencial filtrada.

Lo único que corta los tokens vigentes de un miembro es que el operador lo bloquee: desde ese momento sus llamadas que exigen
sesión responden `401 SESSION_REVOKED` y no puede volver a iniciar sesión mientras dure el bloqueo.

Todas las operaciones de autenticación: [Referencia de API → auth](/api-reference/atlas-api#tag/auth).

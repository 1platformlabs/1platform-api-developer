# Terminal de tarjetas

<p className="lead">Pida una terminal para que su comercio cobre con tarjeta presente. Por la API llena la solicitud, adjunta los documentos, la envía y sigue su estado hasta recibir el código que activa la app de la terminal.</p>

<PromptParaAgente slug="terminal-de-tarjetas" />

## Disponibilidad

El **alta de terminal y el cobro presencial están disponibles**. El comercio cobra con tarjeta presente en la app de la terminal, instalada en su propio teléfono. El cajero completa cada cargo en la app con la tarjeta presente. La API no cobra la tarjeta por su cuenta: envía un cobro remoto a una terminal conectada, con el monto y la referencia de su pedido, y el cajero lo cobra en la app (ver [Cobros remotos a terminal](/docs/saas/1platform-api/terminal-de-tarjetas/cobros-remotos); la plataforma habilita esa función para todos los espacios de trabajo y, mientras tanto, el envío responde `403` con `code` = `terminal_charges_disabled`). Para que los cobros lleguen a su cuenta, un administrador del espacio de trabajo vincula la solicitud aprobada con los identificadores de la terminal y el equipo de la plataforma confirma esa conexión. Desde entonces, cada cobro se registra con un aviso firmado, aparece en el [reporte de cobros](/docs/saas/1platform-api/pagos-en-linea#reporte-de-cobros) con el canal `terminal` y se consulta con `GET /users/terminal-payments/{paymentId}`.

## Cómo funciona

1. Abra una **solicitud** para un comercio con los datos del solicitante. El NIT y la razón social los toma el servidor del comercio: no los envía.
2. Adjunte los documentos que pide su espacio de trabajo, uno por cada `kind`. Si vuelve a adjuntar el mismo `kind`, reemplaza el archivo anterior.
3. Envíe la solicitud. Si falta algo, la llamada responde `422` con la lista de lo pendiente.
4. La solicitud avanza por estos estados:
   - `draft`: la está editando.
   - `submitted`: ya está en manos del proveedor.
   - `submit_failed`: el envío falló. Puede corregir y reintentarlo.
   - `needs_info`: piden correcciones. Vuelva a ser editable.
   - Estados finales: `approved`, `rejected` o `cancelled` (la retiró usted).
5. Cuando la solicitud llega a `approved`, el detalle trae el **código de activación**. El comercio instala la app de la terminal desde el enlace a la tienda y la activa con ese código.

Un administrador del espacio de trabajo registra el resultado de cada solicitud enviada y, ya aprobada, la vincula con los identificadores de la terminal (`PUT /admin/terminal-requests/{requestId}/connection`). Lo hace con las operaciones `/admin/terminal-requests` del mismo tag. Si su integración es el comercio, no las necesita: consulte el estado de su solicitud.

## Qué necesita {#qué-necesitas}

- Las credenciales y los dos tokens de [Inicio rápido](/docs/saas/1platform-api/inicio-rapido).
- Un **comercio** con NIT (`documentNumber`) y rol de **administrador** en su sucursal ([Referencia de API → Businesses & Branches](/api-reference/1platform-api#tag/businesses-branches)). Si falta el NIT, la creación responde `409` con lo que falta.
- El módulo de Terminal de tarjetas encendido para su espacio de trabajo y asignado a su cuenta. Si falta, recibe `403` con `data.code` = `module_disabled`.
- No necesita tener activa la [Facturación electrónica](/docs/saas/1platform-api/facturacion-electronica) para solicitar la terminal.
- Sólo puede haber una solicitud abierta por comercio. Si ya hay una, la creación responde `409`.

## Operaciones

| Operación | Para qué |
|---|---|
| `POST /businesses/{businessId}/terminal-requests` | Abrir la solicitud |
| `PATCH /businesses/{businessId}/terminal-requests/{requestId}` | Corregir los datos mientras está en `draft`, `needs_info` o `submit_failed` |
| `POST /businesses/{businessId}/terminal-requests/{requestId}/documents` | Adjuntar un documento (`multipart/form-data` con `kind` y `file`) |
| `POST /businesses/{businessId}/terminal-requests/{requestId}/submit` | Enviar la solicitud completa |
| `GET /businesses/{businessId}/terminal-requests/{requestId}` | Ver el estado, lo que falta y, si se aprobó, el código de activación |
| `GET /businesses/{businessId}/terminal-requests` | Listar las solicitudes del comercio |
| `POST /businesses/{businessId}/terminal-requests/{requestId}/cancel` | Retirar una solicitud que todavía no se resolvió |
| `GET /terminal-app/{platform}` | Enlace público a la app de la terminal en la tienda |
| `GET /users/terminal-payments/{paymentId}` | Consultar un cobro hecho con la terminal |
| `GET /businesses/{business_id}/terminals` | Listar las terminales conectadas del comercio y saber si los cobros remotos están habilitados |
| `POST /businesses/{business_id}/terminal-charges` | Enviar un cobro remoto a una terminal conectada (idempotente por `idempotency_key`) |
| `GET /businesses/{business_id}/terminal-charges/{charge_id}` | Consultar el estado de un cobro remoto |
| `GET /businesses/{business_id}/terminal-charges` | Listar los cobros remotos del comercio |
| `POST /businesses/{business_id}/terminal-charges/{charge_id}/cancel` | Cancelar un cobro remoto que el cajero todavía no tomó |

Todas las operaciones, incluidas las del administrador del espacio de trabajo: [Referencia de API → Payment Terminals](/api-reference/1platform-api#tag/payment-terminals).

## Eventos

Cuando un cobro remoto termina, 1Platform puede avisarle con el evento `on_terminal_charge_completed`. Se configura en [Webhooks](/docs/saas/1platform-api/plataforma/webhooks#eventos) y su cuerpo está en [Webhooks: cuerpo saliente](/docs/saas/1platform-api/reference/webhooks-payload#terminal-charge-completed).

## Guías

- [Cobros remotos a terminal](/docs/saas/1platform-api/terminal-de-tarjetas/cobros-remotos): enviar un monto a una terminal conectada, seguir su estado y no cobrar dos veces el mismo pedido.
- Para crear el comercio y su sucursal, siga el paso 1 de [Emitir una factura](/docs/saas/1platform-api/facturacion-electronica/emitir-una-factura).

# Formato de respuesta

Casi todas las respuestas usan el mismo sobre. Hay dos excepciones, y un cliente robusto tiene que aceptar las tres
formas.

## El sobre estándar (`{ success, data, msg }`)

Las respuestas exitosas y los errores de negocio llegan así:

```json
{
  "success": true,
  "data": { },
  "msg": "Resumen legible para personas"
}
```

En un error, `success` es `false` y `data` es `null` o trae un código legible por máquina:

```json
{
  "success": false,
  "data": { "code": "PAYMENT_GATEWAY_NOT_CONFIGURED" },
  "msg": "Payment gateway not configured for this user"
}
```

El código legible por máquina viaja en `data.code` en la mayoría de las operaciones. Algunas familias lo envían en la
**raíz** de la respuesta (`code`, con `data: null`): Retiros, Correo, 1Trade y, en Facturación electrónica y en
comercios y sucursales, los errores de activación, de selección de sucursal y de comercio archivado. Lea los dos
lugares: use `data.code` y, si falta, `code`.

```json
{
  "success": false,
  "data": null,
  "msg": "Cash out is not available for this workspace",
  "code": "CASH_OUT_DISABLED"
}
```

Cuando no hay código en ninguno de los dos lugares, el código de estado HTTP es la fuente de verdad y `msg` es lo que
puede mostrar.

## Excepción 1: errores de validación (`422`)

Cuando la solicitud no cumple el esquema (falta un campo, un tipo no corresponde), la respuesta no usa el sobre:

```json
{
  "detail": [
    { "type": "missing", "loc": ["body", "apiKey"], "msg": "Field required", "input": {} }
  ],
  "message": "Validation error in request data"
}
```

`detail[].loc` dice qué campo falló. Corrija la solicitud; no la reintente igual.

## Excepción 2: autenticación y permisos (`401`, algunos `403` y `404`)

Cuando falta un token, venció, fue revocado o el usuario no tiene el rol que exige la operación, la respuesta es un
objeto con `detail`. También usan esta forma los `404` de un recurso que no pertenece a su espacio de trabajo:

```json
{ "detail": "Not authenticated" }
```

El texto de `detail` varía según la causa. Trátelo como informativo: ante un `401`, canjee de nuevo el token que
corresponda; ante un `403` de rol, use el token de un usuario con ese rol.

## Webhooks salientes: sin sobre

Los webhooks que 1Platform envía a su backend no usan ninguna de estas formas: son un objeto plano. Ver
[Webhooks — cuerpo saliente](/docs/saas/1platform-api/reference/webhooks-payload#canonical-payload).

## Qué leer

| Quiere saber… | Lea |
|---|---|
| ¿La solicitud tuvo éxito? | El código de estado HTTP (`2xx` = sí) |
| ¿La respuesta viene en el sobre? | Si existe el campo `success` |
| ¿Qué tipo de fallo de negocio? | `data.code` o, si falta, `code` |
| ¿Qué mostrar a una persona? | `msg` |
| ¿Qué campo de mi solicitud está mal? | `detail[].loc` (sólo en `422`) |

Ver también: [Códigos de error](/docs/saas/1platform-api/reference/error-codes).

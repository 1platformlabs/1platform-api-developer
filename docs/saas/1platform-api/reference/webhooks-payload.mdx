# Webhooks — payload saliente

Esta página documenta lo que **1Platform te envía a ti**, no lo que tú le pides a 1Platform. Por eso no vive en la
[Referencia de API](/api-reference/1platform-api): la especificación OpenAPI describe operaciones que un cliente
invoca, y aquí el cliente es nuestro servidor llamando al tuyo.

La guía que lo pone en contexto —registrar la URL, verificar la firma, responder— es
[Webhooks](/docs/saas/1platform-api/plataforma/webhooks).

## Payload canónico {#canonical-payload}

Si configuraste el evento **sin** `body_template`, el cuerpo tiene esta forma:

```json
{
  "event": "on_approved",
  "transaction_id": "65a1b2c3d4e5f6789abcdef0",
  "external_transaction_id": "PGT123456",
  "status": "approved",
  "amount": 78.00,
  "currency": "GTQ",
  "merchant_amount": 10.00,
  "merchant_currency": "USD",
  "metadata": { "order_id": "..." },
  "merchant_reference": "pedido-1042",
  "reference": "GT123456",
  "timestamp": "2026-04-29T10:35:00+00:00"
}
```

Si configuraste un `body_template`, recibes lo que definiste en él: el cuerpo canónico es lo que llega cuando no hay
plantilla.

`status` es el estado **al que acaba de pasar** la transacción y siempre concuerda con `event`: `on_approved` viaja
con `"status": "approved"`, `on_refunded` con `"refunded"`, y así con los siete. Puedes enrutar por cualquiera de
los dos.

## Campos

| Campo | Origen | Úsalo para |
|---|---|---|
| `event` | 1Platform | Enrutar dentro de tu receptor cuando una URL atiende varios eventos |
| `transaction_id` | 1Platform | Correlacionar con el identificador que guardaste al crear la transacción |
| `external_transaction_id` | Pasarela | Tickets de soporte. Puede venir vacío |
| `status` | 1Platform | Estado al que pasó la transacción. Ver la tabla de abajo |
| `amount` | Pasarela | Sólo informativo: el monto que cobró la pasarela, en su moneda |
| `currency` | Pasarela | La moneda de la pasarela (p. ej. `GTQ`) |
| `merchant_amount` | Tu moneda | **Úsalo para tu contabilidad**: el monto que cotizaste |
| `merchant_currency` | Tu moneda | P. ej. `USD` |
| `metadata` | Reflejado | El objeto libre que enviaste al crear la transacción |
| `merchant_reference` | Reflejado | El identificador libre que enviaste al crear. Úsalo como clave para deduplicar |
| `reference` | Pasarela | Referencia de la pasarela (p. ej. la autorización de la tarjeta) |
| `timestamp` | 1Platform | Hora de la última actualización de la transacción (ISO 8601 con zona horaria) |

:::warning[`currency` cambia de sentido entre la respuesta y el webhook]
En la respuesta de `POST /users/transactions`, `currency` es **tu** moneda (y `currency_provider`, la de la
pasarela). En el webhook es al revés: `currency` es la de la pasarela y la tuya viaja en `merchant_currency`. Nunca
acredites usando `amount`: usa `merchant_amount` y `merchant_currency`.
:::

## Valores de `status`

| `status` | Significado |
|---|---|
| `approved` | El comprador pagó |
| `denied` | El pago fue rechazado |
| `cancelled` | El comprador canceló antes de pagar |
| `expired` | La URL de pago venció sin que se pagara |
| `dismiss` | El comprador cerró la ventana de pago |
| `refunded` | Un pago aprobado fue reembolsado |
| `reversed` | Un pago aprobado fue revertido, por ejemplo por un contracargo |

El estado inicial `created` nunca llega en un webhook. `refunded` y `reversed` sólo pueden llegar después de
`approved`.

## Llevarlo a tu máquina de estados

Si tu sistema maneja pocos estados (por ejemplo `pending`, `paid`, `failed`, `refunded`), este es un mapeo
razonable:

| `status` | Estado en tu sistema |
|---|---|
| `approved` | `paid` (y procede a cumplir el pedido) |
| `denied`, `cancelled`, `expired`, `dismiss` | `failed` |
| `refunded`, `reversed` | `refunded` (revierte el cumplimiento y el registro contable) |

La API todavía no permite **emitir** reembolsos (`POST /users/transactions/{id}/refund` responde `501`). Un
reembolso o una reversión hechos por otra vía te llegan igualmente como `on_refunded` u `on_reversed`.

## Sin sobre de respuesta

Los webhooks **no** vienen en `{ success, data, msg }`: son objetos planos, canónicos o con plantilla. Eso es lo
que permite calcular la firma sobre el cuerpo crudo. Ver
[Formato de respuesta](/docs/saas/1platform-api/reference/response-format).

## Idempotencia de tu lado {#idempotency-on-the-merchant-side}

La entrega es **al menos una vez**, con reintentos; ver
[Reintentos y entrega](/docs/saas/1platform-api/reference/retry-and-delivery). Tu receptor **debe** deduplicar.

La clave recomendada es `(transaction_id, event)`. Si envías `merchant_reference` al crear la transacción, también
puedes deduplicar por `(merchant_reference, event)` para alinearte con tus propios identificadores de pedido.

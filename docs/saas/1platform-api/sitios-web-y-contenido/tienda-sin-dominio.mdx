# Crear una tienda sin dominio propio

Una tienda servida por la plataforma puede crearse sin dominio. El nombre de la tienda determina su dirección, con la forma `<identificador>.1platform.pro`, y el dominio propio se conecta después a la misma tienda, sin volver a cargar el catálogo. Este recorrido sólo aplica al tipo `store`; los sitios de contenido y WordPress siguen necesitando un dominio.

:::note

Estas operaciones dependen de que la capacidad esté activa en su entorno. Si no lo está, la consulta de disponibilidad y el alta sin dominio responden `403` con `PROVISIONING_PLATFORM_ADDRESS_DISABLED`. La Referencia de API las incluye cuando el contrato publicado las contiene.

:::

Todas las llamadas usan los dos tokens de [Inicio rápido](/docs/saas/1platform-api/inicio-rapido) y el módulo de sitios web habilitado.

```bash
export BASE_URL="https://api-qa.1platform.pro/api/v1"
export APP_TOKEN="ak-..."     # su token de aplicación
export USER_TOKEN="sk-..."    # el token del usuario dueño de la tienda
```

## 1. Comprobar la dirección

`GET /provisioning/platform-address` recibe el nombre de la tienda en `site_name` y devuelve el identificador y la dirección que resultan de él. No reserva nada: sirve para mostrar al usuario si el nombre está libre antes de crear.

```bash
curl -G "$BASE_URL/provisioning/platform-address" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "x-user-token: $USER_TOKEN" \
  --data-urlencode "site_name=Aurum Labs"
```

```json
{
  "success": true,
  "data": {
    "slug": "aurum-labs",
    "host": "aurum-labs.1platform.pro",
    "available": true,
    "reason": null
  },
  "msg": "ok"
}
```

Cuando `available` es `false`, `reason` indica el motivo: `taken` (la dirección ya existe), `reserved` (el identificador no está disponible) o `invalid`. La respuesta nunca dice a quién pertenece una dirección ocupada; pida otro nombre. Si el nombre no produce un identificador válido, `slug` y `host` llegan vacíos con `reason` en `invalid`.

Donde la capacidad no está disponible, esta consulta responde `403` con `PROVISIONING_PLATFORM_ADDRESS_DISABLED`. La disponibilidad es una lectura de un instante: el alta la vuelve a comprobar y puede responder `409` aunque la consulta haya dicho `true`.

## 2. Crear la tienda

`POST /provisioning/tenants` sin `domain` crea la tienda en la dirección de la plataforma. `kind` es `store`.

```bash
curl -X POST "$BASE_URL/provisioning/tenants" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "x-user-token: $USER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"kind": "store", "site_name": "Aurum Labs", "language": "es"}'
```

La respuesta es `202` con el trabajo de creación, igual que el alta con dominio. Consúltelo con `GET /provisioning/tenants/{job_id}` hasta que termine y no anuncie la tienda antes. La configuración de cobros se completa por separado.

| Estado | `code` | Qué significa |
|---|---|---|
| `409` | `PROVISIONING_SITE_NAME_TAKEN` | La dirección que produce el nombre ya existe. Elija otro nombre |
| `403` | `PROVISIONING_PLATFORM_ADDRESS_DISABLED` | El alta en dirección de la plataforma no está disponible en este entorno |
| `409` | `PROVISIONING_DOMAIN_RESERVED` | Alta con dominio: ese dominio tiene una conexión de dominio activa en otra tienda |

Una tienda creada así aparece en `GET /users/websites/mine` con `platform_address: true`. Esa marca la identifica como una tienda cuyo dominio es una dirección de la plataforma y la distingue de las que ya tienen dominio propio.

## 3. Conectar su dominio

Cuando el dueño tenga un dominio, `PUT /users/websites/{website_id}/custom-domain` inicia la conexión sobre la misma tienda. Sólo aplica a tiendas en dirección de la plataforma.

```bash
curl -X PUT "$BASE_URL/users/websites/$WEBSITE_ID/custom-domain" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "x-user-token: $USER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain": "aurumlabs.com"}'
```

La respuesta es `202` con el sitio serializado. Su campo `domain_connection` informa la conexión más reciente que no fue cancelada, o `null`:

```json
{
  "domain_connection": {
    "domain": "aurumlabs.com",
    "platform_host": "aurum-labs.1platform.pro",
    "state": "pending",
    "nameservers": ["ns1.example-dns.net", "ns2.example-dns.net"],
    "last_error_code": null
  }
}
```

| `state` | Qué significa |
|---|---|
| `pending` | La conexión espera la delegación. La tienda sigue en su dirección de la plataforma |
| `promoting` | Se verificó la delegación y se está activando el dominio. Ya no puede cancelarse |
| `done` | El dominio propio es la dirección principal de la tienda |
| `cancelling` | La cancelación está en curso |

`nameservers` puede llegar vacío mientras la plataforma todavía no los asignó; consulte de nuevo `GET /users/websites/{website_id}`. Configure en el registro de su dominio los nameservers que la respuesta devuelva (los del ejemplo son ilustrativos). `platform_host` es la dirección de la plataforma de la tienda: cuando la conexión llega a `done`, esa dirección redirige al dominio. `last_error_code` guarda el último motivo de fallo de la verificación, si lo hubo, y es `null` si no lo hubo.

:::warning

Delegar los nameservers mueve todo el DNS del dominio a la plataforma. Antes de hacerlo, revise y recree los registros de correo y de los demás servicios que use el dominio.

:::

Cuando la conexión termina, las páginas de la tienda en la dirección de la plataforma redirigen de forma permanente al dominio propio, conservando la ruta y los parámetros. Otras rutas técnicas, como `/sitemap.xml`, `/signout` y `/api/*`, siguen respondiendo en la dirección anterior. El dominio propio sirve la misma tienda.

| Estado | `code` | Qué significa |
|---|---|---|
| `404` | sin `code` | La tienda no existe o no es suya |
| `409` | `WEBSITE_DOMAIN_TAKEN` | Ese dominio ya está en uso en otra tienda o sitio |
| `409` | `WEBSITE_NOT_ON_PLATFORM_ADDRESS` | La tienda ya tiene dominio propio; no está en una dirección de la plataforma |
| `409` | `WEBSITE_DOMAIN_PENDING` | Ya hay una conexión pendiente para esta tienda |
| `422` | `WEBSITE_DOMAIN_NOT_OWNED` | El dominio no está activo ni verificado en la cuenta del dueño de la tienda |

El dominio tiene que estar registrado en la cuenta del dueño o verificado mediante [Dominios y correo](/docs/saas/1platform-api/dominios-y-correo); escribir su nombre no demuestra propiedad.

## 4. Cancelar una conexión pendiente

`DELETE /users/websites/{website_id}/custom-domain` cancela la conexión mientras está en `pending`.

```bash
curl -X DELETE "$BASE_URL/users/websites/$WEBSITE_ID/custom-domain" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "x-user-token: $USER_TOKEN"
```

La respuesta es `202` con el sitio serializado: `domain_connection.state` queda en `cancelling` o, si la cancelación ya terminó, `domain_connection` es `null`. La tienda permanece en su dirección de la plataforma.

| Estado | `code` | Qué significa |
|---|---|---|
| `404` | sin `code` | La tienda no existe o no es suya |
| `409` | `WEBSITE_DOMAIN_PROMOTING` | La activación ya empezó y no puede cancelarse |
| `409` | `WEBSITE_DOMAIN_NOT_PENDING` | No hay una conexión pendiente que cancelar |

Si ya delegó los nameservers antes de cancelar, restaure en el registro de su dominio los nameservers anteriores: cancelar la conexión no los devuelve.

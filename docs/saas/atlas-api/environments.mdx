# Entornos

La Atlas API corre en dos entornos con la misma API versionada bajo `/api/v1`.

| Entorno | URL base | OpenAPI |
|---|---|---|
| **Producción** | `https://atlas-api.1platform.pro/api/v1` | `https://atlas-api.1platform.pro/openapi.json` |
| **QA** | `https://atlas-api-qa.1platform.pro/api/v1` | `https://atlas-api-qa.1platform.pro/openapi.json` |

Las guías usan estas variables:

```bash
export ATLAS_BASE="https://atlas-api-qa.1platform.pro/api/v1"
export TENANT_SLUG="<slug-de-tu-tenant>"
export ATLAS_JWT="<access_token-de-la-sesion>"
```

## Qué cambia entre QA y producción

- **Los datos no se comparten.** Tenants, miembros, catálogo y derechos de acceso de QA no existen en producción, y al
  revés. El slug de su tenant de pruebas se lo da el equipo de 1Platform Labs; verifíquelo igual que en producción
  ([Resolución de tenant](/docs/saas/atlas-api/tenant-resolution)).
- **El cuerpo estándar del límite de uso sólo está activo en producción.** En QA el `429` llega con un `detail` de texto
  y sin el código `RATE_LIMITED`, así que no use QA para probar su manejo del `429` ([Límites de uso](/docs/saas/atlas-api/rate-limits)).
- **Las credenciales se emiten por entorno.** Pida al equipo de 1Platform Labs la cuenta de operador, la clave de
  integración y el secreto de webhook de cada entorno por separado.

## Prefijo de ruta y OpenAPI

Toda operación vive bajo `/api/v1`; la especificación OpenAPI se sirve en la **raíz** del host, no bajo `/api/v1`. Genere
sus tipos y clientes desde ella en lugar de escribir las formas a mano. Para explorar y probar cada operación, use la
[Referencia de API](/api-reference/atlas-api).

## Siempre envíe `X-Tenant-Slug` {#siempre-envía-x-tenant-slug}

La URL base no identifica a ningún tenant. Si llama a la API desde su servidor o un script, envíe siempre
`X-Tenant-Slug`; llamar al dominio del tenant no le lleva a la API. Detalle en
[Resolución de tenant](/docs/saas/atlas-api/tenant-resolution).

# Autenticación

Toda llamada protegida lleva dos tokens: el **token de aplicación** (`Authorization: Bearer $APP_TOKEN`), que
identifica a su espacio de trabajo, y el **token de usuario** (`x-user-token: $USER_TOKEN`), que identifica a la
persona en cuyo nombre actúa. Los dos son JWT de corta duración y se obtienen canjeando claves de larga vida: la
clave de aplicación (`ak-…`) y la clave de usuario (`sk-…`). Cada paso necesita el resultado del anterior, y por eso
el orden importa.

Hay dos caminos hacia el token de usuario: **servidor a servidor** (su backend da de alta al usuario y guarda su
clave) y **enlace mágico** (la persona entra con un enlace que recibe por correo). De dónde sale su clave de
aplicación está en [Inicio rápido → Consiga sus claves](/docs/saas/1platform-api/inicio-rapido#claves).

## Paso 1 — Token de aplicación

Sin token de aplicación no hay nada más: ni alta de usuario ni token de usuario. Canjee su clave de aplicación:

```bash
curl -X POST "$BASE_URL/auth/token" \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "'"$APP_API_KEY"'"}'
```

Guarde `data.access_token` como `$APP_TOKEN` y `data.expires_in` (segundos) para saber cuándo renovarlo. Un `401`
indica que la clave no es válida, fue revocada o pertenece al otro entorno. Un `429` indica que superó el límite de
este canje: 10 solicitudes por minuto desde una misma dirección, y además un tope por clave.

[Referencia de API → Get App Token](/api-reference/1platform-api#tag/get-app-token)

## Paso 2 — Alta del usuario desde su backend {#paso-2--alta-del-usuario-desde-tu-backend}

Si su backend es quien conoce a sus usuarios, déelos de alta con el token de aplicación. La respuesta trae la clave
de usuario (`sk-…`) que el paso siguiente necesita. La misma llamada deja creado el registro de saldo y la
suscripción del usuario: no hay un paso aparte para eso.

```bash
curl -X POST "$BASE_URL/users" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email": "carlos.mendez@example.com"}'
```

Guarde `data.api_key` como `$USER_API_KEY` en un lugar seguro: es la credencial de ese usuario en este flujo.
`currency` es opcional; si la omite, el saldo principal del usuario usa la primera moneda del catálogo de su
espacio de trabajo. Un `409` indica que ese correo ya tiene cuenta: la API no devuelve la clave de un usuario
existente, así que pídele que entre por enlace mágico (paso 4) o que cree su propia clave de usuario desde la
sección **API** del Panel. Un `400` indica que el correo no tiene un formato válido.

:::warning[La clave del alta se renueva cuando la persona verifica su correo]
Si después la misma persona **entra al Panel con un enlace mágico** (es decir, verifica que el correo es
suyo), en ese primer ingreso la plataforma desactiva todas las credenciales emitidas antes de la
verificación —incluida la `api_key` que devolvió este paso y cualquier credencial creada con ella— y emite
una nueva que no se entrega por la API. Desde ese momento `POST /users/token` con la clave anterior responde
`401`.

Es una protección: como el token de aplicación es público, cualquiera podría dar de alta el correo de otra
persona y quedarse con su clave. Si su integración guarda la `api_key` del alta, no combine ese flujo con que
la persona entre al Panel con la misma cuenta; si tiene que hacerlo, después de su primer ingreso la persona
solicita acceso de desarrollador desde el Panel y un administrador del espacio de trabajo lo aprueba.
:::

[Referencia de API → Users & Tokens](/api-reference/1platform-api#tag/users-tokens)

## Paso 3 — Token de usuario

Canjee la clave de usuario por un token de usuario. Este es el valor que viaja en `x-user-token` junto al token de
aplicación del paso 1.

```bash
curl -X POST "$BASE_URL/users/token" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"apiKey": "'"$USER_API_KEY"'"}'
```

Guarde `data.access_token` como `$USER_TOKEN`. La clave de usuario es reutilizable: cada vez que necesite un token
nuevo vuelve a este canje, nunca a crear el usuario. El límite de este canje es de 10 por minuto **por token de
aplicación**, y lo comparten todos los usuarios que canjea con ese mismo token: canjee una vez por usuario y
reutiliza el resultado (ver [Mantener los tokens vigentes](#cache-de-tokens)).

[Referencia de API → Users & Tokens](/api-reference/1platform-api#tag/users-tokens)

## Paso 4 — Alternativa: enlace mágico

Los pasos 2 y 3 sirven cuando su backend actúa en nombre de usuarios que ya conoce. Cuando quien entra es una
persona frente a una pantalla y no quiere manejar contraseñas, use el enlace mágico: un correo con un enlace de un
solo uso.

```bash
curl -X POST "$BASE_URL/auth/user/magic-link/request" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"email": "'"$USER_EMAIL"'"}'
```

La respuesta es siempre `200` y no confirma si el correo existe, para que nadie pueda averiguar qué cuentas hay. El
enlace del correo abre la ruta `/auth/verify?token=…` del panel de su espacio de trabajo y vence a los 10 minutos.
La página que recibe ese `token` lo canjea con `POST /auth/user/magic-link/verify` (token de aplicación, cuerpo
`{"token": "…"}`), que devuelve un `access_token` —se usa como token de usuario— y un `refresh_token`.

- `410`: el enlace ya se usó o venció. Pida uno nuevo; no repita la verificación.
- `403` con `data.code` `account_inactive`: un administrador desactivó la cuenta.
- `429` en la solicitud: superó 10 solicitudes por minuto desde su servidor. Aparte, cada dirección recibe como
  máximo 3 enlaces cada 10 minutos; pasado ese tope la llamada sigue respondiendo `200` pero el correo no sale, así
  que no reintente en bucle.

[Referencia de API → User Authentication](/api-reference/1platform-api#tag/user-authentication)

## Paso 5 — Primera llamada autenticada

Con `$APP_TOKEN` y `$USER_TOKEN` (o el `access_token` del enlace mágico) ya puede llamar a cualquier operación
protegida. Esta confirma que los dos tokens funcionan juntos:

```bash
curl "$BASE_URL/users/profile" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "x-user-token: $USER_TOKEN"
```

Un `401` indica que alguno de los dos tokens falta, venció o no es válido: repita el paso que lo generó. A partir
de aquí, todas las operaciones protegidas se llaman con estos mismos dos headers.

[Referencia de API → My Profile](/api-reference/1platform-api#tag/my-profile)

## Paso 6 — Renovar y cerrar la sesión

Cómo se termina una sesión depende del camino que usó. Si entró por enlace mágico, renueve el par antes de
que venza el token de acceso con `POST /auth/user/refresh`:

```bash
curl -X POST "$BASE_URL/auth/user/refresh" \
  -H "Authorization: Bearer $APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"token": "'"$REFRESH_TOKEN"'"}'
```

Cada renovación invalida el `refresh_token` anterior. Un `409` indica que se presentó uno ya usado: trátelo como un
posible robo de sesión y vuelve a autenticar a la persona. Un `401` indica que el `refresh_token` venció. Para cerrar
la sesión, llame a `POST /auth/user/logout` con los dos tokens en los headers y, en el cuerpo, el token que quiere
revocar (`{"token": "…"}`).

En el camino servidor a servidor (pasos 2 y 3) no hay nada que renovar: para cortar todas las sesiones de un
usuario llama a `POST /users/revoke-tokens` con sus dos tokens. Todo token de usuario emitido hasta ese momento deja
de valer y hace falta un canje nuevo (paso 3).

Guarde los `refresh_token` en cookies `httpOnly` seguras o en el almacenamiento seguro del sistema (Keychain,
Keystore), nunca en `localStorage`, que cualquier script de la página puede leer.

[Referencia de API → User Authentication](/api-reference/1platform-api#tag/user-authentication) ·
[Referencia de API → Users & Tokens](/api-reference/1platform-api#tag/users-tokens)

## Mantener los tokens vigentes {#cache-de-tokens}

Los canjes de los pasos 1 y 3 están limitados a 10 por minuto, así que pedir un token por llamada es la causa más
común de un `429` durante el desarrollo. El patrón que evita el problema:

1. Guarde cada token junto con su vencimiento: el momento del canje más `expires_in`.
2. Reutilícelo en todas las llamadas mientras le quede más de un minuto de vida (`expires_in − 60` segundos).
3. Renuévelo antes de que venza, no después de recibir un `401`. Si aun así llega un `401`, canjee de nuevo una
   sola vez y repita la llamada; si vuelve a fallar, el problema es la clave, no el token.
4. En un proceso con varios hilos o instancias, comparta la caché entre ellos para que no canjeen todos a la vez.

# Webhooks

Atlas **recibe** un webhook: `POST /webhooks/entitlement`. Lo llama el proveedor de pagos configurado para el tenant
(hoy, Bowerbird, de 1Platform Labs) para avisar que un miembro ganó o perdió acceso. Atlas verifica la firma, descarta los
reenvíos y escribe o borra el [derecho de acceso](/docs/saas/atlas-api/entitlements) correspondiente.

> No es un endpoint para integradores en general: sólo lo usa quien opera la integración de pagos de un tenant. El secreto
> de firma lo entrega el equipo de 1Platform Labs ([Referencia de API → webhooks](/api-reference/atlas-api#tag/webhooks)).

## Paso 1 — Firma con el secreto de tu tenant

Cada tenant tiene **su propio secreto de webhook**. Atlas elige con qué secreto verificar leyendo `data.tenant_id` del
cuerpo, así que ese campo es obligatorio: sin él, o con el identificador de otro tenant, la firma no verifica.

La firma es un HMAC-SHA256 en hexadecimal sobre el timestamp, un punto y los **bytes exactos** del cuerpo. Fírmalo antes de
enviarlo y no lo vuelvas a serializar: cualquier cambio de espacios u orden rompe la firma.

```text
firma = hex( HMAC_SHA256(secreto_del_tenant, "{timestamp}." + cuerpo_crudo) )
```

## Paso 2 — Envía el evento

La firma va en `x-bowerbird-signature` (con o sin el prefijo `sha256=`), el timestamp en `x-bowerbird-timestamp` y,
opcionalmente, el identificador del evento en `x-bowerbird-event-id`. Son los nombres por defecto; un despliegue puede
configurar otros, así que confírmalos con el equipo de 1Platform Labs.

```bash
curl -s -X POST "$ATLAS_BASE/webhooks/entitlement" \
  -H "Content-Type: application/json" \
  -H "x-bowerbird-signature: sha256=<FIRMA_HEX>" \
  -H "x-bowerbird-timestamp: 1782000000" \
  -H "x-bowerbird-event-id: evt_01H…" \
  -d '{"id":"evt_01H…","type":"access.granted","occurred_at":"2026-06-18T12:00:00Z","data":{"tenant_id":"<TENANT_ID>","member_id":"<MEMBER_ID>","scope":"plan","scope_ref":"anual","expires_at":null}}'
```

Una firma o un timestamp ausente o incorrecto responde `401 WEBHOOK_SIGNATURE_INVALID`.

## Qué tipos de evento acepta

| `type` | Efecto en Atlas |
|---|---|
| `access.granted` | Concede el derecho de acceso de `data.scope` y `data.scope_ref`. |
| `access.revoked`, `subscription.cancelled`, `rental.expired` | Revocan el derecho de acceso de `data.scope_ref` (y de `data.scope`, si lo envías). |
| `subscription.renewed`, `subscription.payment_failed`, `rental.started` | No cambian derechos de acceso; algunos disparan un correo al miembro. |

Envía sólo estos siete tipos. Cualquier otro valor de `type`, o un cuerpo que no sea JSON, se rechaza con un error del
servidor (`5xx`) y no se registra: reintentarlo no lo arregla.

## Qué garantiza Atlas

- **Deduplicación.** Atlas registra cada evento por su identificador: el header de id de evento si lo envías y, si no, el
  `id` del cuerpo. Un reenvío del mismo identificador responde `2xx` con `deduplicated: true` sin volver a aplicar el
  cambio. Usa un identificador estable por evento lógico para que tus reintentos sean seguros.
- **Sin control de antigüedad.** Atlas no rechaza timestamps viejos; la protección contra reenvíos es la deduplicación.
- **Un `2xx` significa que Atlas tiene el evento.** Reintenta sólo ante `5xx` o un fallo de red. Los correos al miembro se
  envían después de guardar el cambio y su fallo nunca convierte el webhook en un error.
- **Los datos incompletos no se reprocesan.** Un evento sin `tenant_id` o `member_id`, una concesión sin `scope` o
  `scope_ref`, o una revocación sin `scope_ref` se registra y responde `2xx` sin efecto. Como ya quedó registrado, reenviarlo
  con el mismo identificador tampoco tendrá efecto: corrige el origen y envía un evento nuevo.
